# Convene Technical Design Doc

## 1. Product Scope

Convene's goal is to turn user availability into real social plans by handling the coordination layer: understanding preferences, choosing compatible people, selecting activities, finding time, and generating hangouts.

For the MVP, the goal is not to build the full social platform. The goal is to prove the core loop: a user gives Convene preferences and available time, and Convene produces a thoughtful plan with a compatible person.

### Scope Principle

The MVP should optimize for a believable end-to-end experience over technical completeness. It is better to have one polished flow from onboarding to generated hangout than many partially working integrations.

### Tier 1: Essential MVP

These are required to demonstrate the core product loop.

- User onboarding form
- Basic preference profile generation
- Seeded user database
- Manual weekly availability input
- One-on-one matching with a new person
- Basic compatibility scoring
- Automatic activity selection
- Calendar overlap detection using stored availability
- Generated hangout plan
- Simple post-hangout feedback
- Minimal friends list or connection history

### Tier 2: Strong Demo Features

These are not strictly required, but they make the product feel much more compelling.

- Explainable compatibility score
- Controlled-random matching instead of always picking the top match
- Online vs. in-person planning branches
- Existing-friend reconnection flow
- Simple social graph visualization
- "Plan my week" button
- Basic social-time allocation, such as new people vs. existing friends
- Activity preference refinement after feedback
- Mock calendar view showing generated events

### Tier 3: Nice to Have

These improve polish or depth but should only be built after the core loop works.

- Group matching with 3+ people
- More detailed preference memory model
- Activity intensity or novelty slider
- Travel distance preferences
- Budget preferences
- Better onboarding conversation
- Lightweight notifications/reminders
- More nuanced feedback questions
- Profile correction UI
- Multiple generated plan options

### Tier 4: Likely Out of Scope for MVP

These are valuable long term but too expensive or risky for the first version.

- Real Google Calendar write access
- Live venue search
- Real-time maps/travel-time optimization
- Live event discovery
- Payments or reservations
- User-to-user chat
- Push notifications
- Production moderation system
- International matching
- Translation
- Complex group optimization
- Production-grade recommendation infrastructure
- Advanced privacy, abuse, and safety tooling

## 2. Core Entities

Convene is built around a small set of core entities. These represent users, their preferences, their availability, their relationships, and the hangouts generated by the system.

The main architectural distinction is that the user is not the profile. The user is the account/person record. The profile is the system's current understanding of that person. Preference memories are the smaller, updateable pieces of that understanding.

This separation helps avoid pigeonholing because Convene can update, weaken, contradict, or replace individual memories without rewriting the whole person.

### User

Represents a person using Convene.

The user entity should stay relatively small. Most evolving information about the person should live in related entities such as preference memories, availability blocks, friendships, and feedback.

Core fields:

- `id`
- `name`
- `age`
- `location`
- `timezone`
- `max_travel_distance`
- `created_at`

Example:

```json
{
  "id": "user_001",
  "name": "Maya",
  "age": 21,
  "location": {
    "city": "Atlanta",
    "region": "GA",
    "lat": 33.7756,
    "lng": -84.3963
  },
  "timezone": "America/New_York",
  "max_travel_distance": {
    "value": 5,
    "unit": "miles"
  },
  "created_at": "2026-09-23T18:30:00Z"
}
```

### Preference Profile

Represents what Convene currently understands about a user.

This should not be a flat list of interests. The profile should combine structured fields, flexible preference memories, and raw evidence from onboarding or feedback.

Possible fields:

- `user_id`
- `summary`
- `interest_index`
- `preference_memory_ids`
- `profile_embedding`
- `last_updated`

`interest_index` is a lightweight derived cache used for filtering and retrieval. It should be generated from preference memories and should not be treated as the source of truth for what a user likes.

`profile_embedding` is a derived vector representation of the profile summary and preference memories. It is used for semantic retrieval and approximate similarity search, not as the final source of truth for matching.

The preference profile summarizes the user and helps the system quickly retrieve candidates. Preference memories carry the nuanced evidence, exceptions, and context that should drive final matching decisions.

Example:

```json
{
  "user_id": "user_001",
  "summary": "Maya enjoys low-pressure social activities, especially food, casual games, and creative projects. She is open to meeting new people but prefers smaller groups at first.",
  "interest_index": ["food", "video games", "creative projects", "study sessions"],
  "preference_memory_ids": ["prefmem_101", "prefmem_102", "prefmem_103"],
  "profile_embedding": "[vector stored separately]",
  "last_updated": "2026-09-23T19:05:00Z"
}
```

### Preference Memory

Represents one nuanced thing Convene has learned about the user.

Examples:

- The user likes low-pressure co-op games.
- The user enjoys trying new food places but avoids expensive restaurants.
- The user prefers one-on-one hangouts when meeting new people.
- The user likes outdoor activities but not in extreme heat.

Possible fields:

- `id`
- `user_id`
- `topic`
- `summary`
- `evidence`
- `attributes`
- `memory_embedding`
- `confidence`
- `source`
- `created_at`
- `last_updated`

Example:

```json
{
  "id": "prefmem_101",
  "user_id": "user_001",
  "topic": "video games",
  "summary": "Enjoys games as a low-pressure way to collaborate and talk.",
  "evidence": [
    "mentioned Valorant",
    "likes co-op Minecraft",
    "enjoys story-driven RPGs",
    "dislikes high-pressure ranked matches"
  ],
  "attributes": {
    "preferred_modes": ["co-op", "casual competitive"],
    "intensity": "low-to-medium",
    "voice_chat": "optional"
  },
  "memory_embedding": "[vector stored separately]",
  "confidence": 0.72,
  "source": "onboarding_llm_followup",
  "created_at": "2026-09-23T18:45:00Z",
  "last_updated": "2026-09-23T18:45:00Z"
}
```

The top-level structure can stay consistent across memories, but `attributes` should be flexible and domain-specific. For food, `attributes` might include cuisines, dietary constraints, spice tolerance, and price range. For hiking, it might include difficulty, distance, pace, and weather sensitivity. For games, it might include preferred modes, intensity, platform, and voice chat preference.

`memory_embedding` is a derived vector representation of the memory's topic, summary, evidence, and key attributes. It is used to retrieve relevant memories for updates, matching, activity planning, and explanation generation.

### Activity Preference

Represents a user's desired or undesired activity direction for a specific matching request.

Activity preferences should not be stored as plain strings internally. A user or profile default may start as natural language, but the system should normalize that input into structured preferences before matching and activity planning.

Possible fields:

- `id`
- `label`
- `polarity`
- `source`
- `activity_type`
- `tags`
- `attributes`
- `strength`
- `raw_text`

Field notes:

- `polarity`: `include` or `exclude`.
- `source`: where the preference came from, such as `user_selected`, `profile_default`, `availability_block`, or `llm_normalized`.
- `activity_type`: broad activity family, such as `food`, `games`, `outdoors`, `study`, or `creative`.
- `tags`: normalized tags used for retrieval and scoring.
- `attributes`: flexible domain-specific details.
- `strength`: how strongly this should influence planning, from `0.0` to `1.0`.
- `raw_text`: the original phrase, if this came from natural language.

## 3. Preference Profile Model

The preference model is responsible for representing what Convene knows about a user without reducing them to shallow tags.

The system should support both fast retrieval and nuanced reasoning:

- Fast retrieval asks: "Who might be worth considering?"
- Nuanced reasoning asks: "Does this specific person, activity, and setting actually fit?"

To support both, Convene separates broad indexes from detailed preference memories.

### Design Goals

- Preserve nuance from user language.
- Avoid treating broad categories as complete identities.
- Allow preferences to change over time.
- Store evidence for why the system believes something.
- Support both explicit onboarding answers and feedback-based learning.
- Keep deterministic constraints separate from fuzzy preferences.

### Preference Memory Structure

A preference memory represents one specific learned claim about a user.

Example:

```json
{
  "id": "prefmem_101",
  "user_id": "user_001",
  "topic": "video games",
  "summary": "Enjoys games as a low-pressure way to collaborate and talk.",
  "evidence": [
    "mentioned Valorant",
    "likes co-op Minecraft",
    "enjoys story-driven RPGs",
    "dislikes high-pressure ranked matches"
  ],
  "attributes": {
    "preferred_modes": ["co-op", "casual competitive"],
    "intensity": "low-to-medium",
    "voice_chat": "optional"
  },
  "memory_embedding": "[vector stored separately]",
  "confidence": 0.72,
  "source": "onboarding_llm_followup",
  "created_at": "2026-09-23T18:45:00Z",
  "last_updated": "2026-09-23T18:45:00Z"
}
```

### Evidence and Confidence

Confidence should be attached to specific memories, not the whole profile.

A memory based on one vague onboarding answer should have lower confidence than a memory supported by repeated behavior and feedback.

Possible confidence inputs:

- Explicit user statement
- Repeated user behavior
- Post-hangout feedback
- Recency
- Contradictory evidence
- User correction

### Memory Retrieval

Preference memories should be retrieved directly when the system needs fine-grained context.

`profile_embedding` is useful for broad user-to-user similarity, but it is too coarse for questions like "Which memories are relevant to this rock climbing answer?" or "Why is this activity a good fit?" For those tasks, Convene should search across `memory_embedding` values.

Retrieval layers:

- `interest_index`: cheap broad filter for obvious topics.
- `profile_embedding`: broad user-to-user similarity.
- `memory_embedding`: granular retrieval of specific preference memories.
- `Preference Memory`: source-of-truth nuanced record.

#### Retrieval Inputs

Memory retrieval should accept a small structured request:

```json
{
  "user_id": "user_001",
  "query_text": "I'd try rock climbing, but only with friends and nothing too intense.",
  "query_context": "notification_question",
  "candidate_topics": ["rock climbing", "outdoor activities", "exercise", "adventurous activities"],
  "max_results": 5
}
```

Fields:

- `user_id`: the user whose memories should be searched.
- `query_text`: the new user signal, activity, match explanation request, or planning question.
- `query_context`: where the query came from, such as `onboarding`, `notification_question`, `post_hangout_feedback`, `matching`, or `activity_planning`.
- `candidate_topics`: optional topic hints from the UI, notification template, or upstream classifier.
- `max_results`: default to `5` for memory updates.

#### Retrieval Algorithm

For memory updates, use this default retrieval flow:

1. Build a retrieval query from the new signal.

```text
query_text + candidate_topics + query_context
```

2. Generate an embedding for the retrieval query.
3. Search the user's active preference memories by cosine similarity against `memory_embedding`.
4. Fetch the top `5` memories by embedding similarity.
5. Also fetch exact or fuzzy topic matches from `topic` and `interest_index`, if any exist.
6. Merge the embedding results and topic results.
7. Deduplicate by `memory_id`.
8. Rerank using a weighted score.
9. Pass only the final top `5` memories into the LLM update call.

Suggested rerank score:

```text
score =
  (0.70 * embedding_similarity) +
  (0.15 * topic_match_score) +
  (0.10 * recency_score) +
  (0.05 * confidence_score)
```

Scoring notes:

- `embedding_similarity` should be normalized to `0.0-1.0`.
- `topic_match_score` should be `1.0` for exact topic match, `0.5` for related topic match, and `0.0` otherwise.
- `recency_score` should be higher for recently created or recently reinforced memories.
- `confidence_score` should be the memory's current confidence value.

Default thresholds:

- If a memory has `embedding_similarity < 0.35` and no topic match, exclude it.
- If fewer than `3` memories pass the threshold, allow the best lower-scoring memories until either `3` memories are included or no memories remain.
- If no memories are found, call the LLM with an empty relevant-memory list and allow only `create_memory` or `no_op`.

The default `max_results` should be `5`. This keeps the LLM context focused and reduces the chance that unrelated memories drift.

#### Retrieval Output

The retrieval step should return compact memory records, not the entire user profile.

Example output:

```json
{
  "query": "I'd try rock climbing, but only with friends and nothing too intense.",
  "memories": [
    {
      "id": "prefmem_204",
      "topic": "outdoor activities",
      "summary": "Open to outdoor activities when they are beginner-friendly and social.",
      "evidence": [
        "said hiking sounded fun if the trail was easy",
        "preferred social pace over intense exercise"
      ],
      "attributes": {
        "difficulty": "easy",
        "pace": "social"
      },
      "confidence": 0.66,
      "retrieval_score": 0.82
    }
  ]
}
```

Only include fields needed for reasoning:

- `id`
- `topic`
- `summary`
- `evidence`
- `attributes`
- `confidence`
- `last_updated`
- `retrieval_score`

Do not pass unrelated memories, full raw onboarding transcripts, private calendar details, or the full profile unless the specific operation requires them.

#### Example

```text
New answer:
"I'd try rock climbing, but only with friends and nothing too intense."

Relevant memories to retrieve:
- Outdoor activities
- Exercise or fitness comfort
- Novelty/adventurousness
- Group comfort
- Intensity tolerance
```

The system should retrieve only relevant memories before asking the LLM to reason about an update. It should not pass the user's entire memory history into every update call.

### Memory Update Flow

When a user provides a new signal, such as answering a notification question or giving feedback after a hangout, Convene should update memories through a controlled patch flow.

```text
New user signal
 -> retrieve relevant memories
 -> LLM proposes memory operation
 -> backend validates operation
 -> apply memory changes
 -> refresh derived profile fields and embeddings
```

The LLM should propose memory operations rather than directly rewriting the user's profile.

A single user signal may affect multiple memories. For example, "I'd try rock climbing, but only with friends and nothing too intense" could create a rock climbing memory, update an outdoor activities memory, and update a social comfort memory. For that reason, the LLM should return a memory patch containing a list of operations, not a single operation.

Possible operations:

- `create_memory`
- `update_memory`
- `merge_memories`
- `weaken_memory`
- `archive_memory`
- `no_op`

#### Memory Operation Contract

Each memory update should be returned as structured JSON. The LLM chooses proposed operations, but backend code validates and applies them.

Top-level patch shape:

```json
{
  "patch_id": "patch_701",
  "user_id": "user_001",
  "source": "notification_question",
  "input_summary": "User said they would try rock climbing if invited by friends, but only in a low-intensity setting.",
  "operations": [],
  "requires_user_confirmation": false
}
```

Patch fields:

- `patch_id`: optional client-generated or server-generated ID for tracing.
- `user_id`: user whose memories may be changed.
- `source`: where the new signal came from.
- `input_summary`: concise summary of the new user signal.
- `operations`: ordered list of memory operations.
- `requires_user_confirmation`: whether the proposed patch should be shown to the user before applying.

The `operations` list may contain zero, one, or many operations. If there is nothing worth changing, the list should contain a single `no_op`.

Every operation should include:

- `operation`: operation name.
- `reason`: short explanation of why this operation is appropriate.
- `source`: where the new signal came from, such as `onboarding`, `notification_question`, or `post_hangout_feedback`.

Operation ordering matters. The backend should apply operations in order after validation. If any operation references the result of a previous operation, it should use a temporary client-side reference such as `temp_memory_1`.

Example multi-operation patch:

```json
{
  "patch_id": "patch_701",
  "user_id": "user_001",
  "source": "notification_question",
  "input_summary": "User said they would try rock climbing if invited by friends, but only in a low-intensity setting.",
  "requires_user_confirmation": false,
  "operations": [
    {
      "operation": "create_memory",
      "temp_id": "temp_memory_1",
      "reason": "Rock climbing is a new specific activity preference not covered by existing memories.",
      "source": "notification_question",
      "memory": {
        "topic": "rock climbing",
        "summary": "Open to trying rock climbing if invited by friends, but prefers beginner-friendly low-intensity settings.",
        "evidence": [
          "answered yes to trying rock climbing if invited, with a low-intensity constraint"
        ],
        "attributes": {
          "experience_level": "beginner",
          "intensity": "low",
          "social_context": "with friends"
        },
        "confidence": 0.62,
        "source": "notification_question"
      }
    },
    {
      "operation": "update_memory",
      "reason": "The answer reinforces an existing broader preference for beginner-friendly outdoor activities.",
      "source": "notification_question",
      "memory_id": "prefmem_204",
      "changes": {
        "append_evidence": [
          "said she would try rock climbing if invited by friends, but nothing too intense"
        ],
        "set_attributes": {
          "difficulty": "beginner-friendly",
          "intensity": "low"
        },
        "confidence_delta": 0.04
      }
    }
  ]
}
```

Backend patch behavior:

- Validate every operation before applying any operation.
- Reject the whole patch if any operation is invalid, unless partial application is explicitly enabled.
- Apply operations in the listed order.
- Resolve temporary IDs to real memory IDs after creation.
- Regenerate embeddings only for created, updated, merged, weakened, or archived memories.
- Refresh derived profile fields once after the full patch is applied, not after each individual operation.
- Store the patch and validation result for debugging/audit.

##### `create_memory`

Creates a new preference memory when the new signal represents a meaningful preference that is not already covered by an existing memory.

Use when:

- No retrieved memory covers the new topic.
- The signal is specific enough to be useful later.
- The signal is not merely a one-off reaction with no planning value.

Required fields:

- `topic`
- `summary`
- `evidence`
- `attributes`
- `confidence`
- `source`

Backend behavior:

- Create a new memory record.
- Generate `memory_embedding` from topic, summary, evidence, and attributes.
- Add or update relevant values in `interest_index`.
- Refresh `profile_embedding` and profile summary if needed.

##### `update_memory`

Updates an existing memory when the new signal adds evidence, refines attributes, or slightly changes confidence.

Use when:

- A retrieved memory already represents the same preference area.
- The new signal strengthens, weakens, or clarifies that memory.
- The update does not require combining two separate memories.

Allowed changes:

- `append_evidence`
- `set_attributes`
- `remove_attributes`
- `confidence_delta`
- `replace_summary`

Backend behavior:

- Validate the referenced `memory_id`.
- Append new evidence rather than deleting old evidence.
- Apply attribute updates.
- Clamp confidence between `0.0` and `1.0`.
- Regenerate the memory's `memory_embedding`.
- Refresh derived profile fields if the update changes the memory meaningfully.

##### `merge_memories`

Combines two or more existing memories when they are redundant or should become one consolidated memory.

Use when:

- Two memories describe the same underlying preference.
- A newer memory duplicates an older one with slightly different wording.
- Separate memories are causing fragmented or contradictory retrieval.

Required fields:

- `memory_ids`
- `merged_memory`
- `reason`

Backend behavior:

- Create or update a canonical memory with the merged summary, evidence, attributes, and confidence.
- Preserve evidence from all merged memories unless it is clearly duplicated.
- Mark non-canonical memories as archived or merged, rather than deleting them.
- Regenerate the canonical `memory_embedding`.
- Refresh derived profile fields.

##### `weaken_memory`

Reduces confidence in an existing memory without removing it.

Use when:

- New evidence partially contradicts an existing memory.
- A user gives feedback that suggests the preference is weaker than expected.
- A memory is old and no longer reinforced.

Required fields:

- `memory_id`
- `confidence_delta`
- `evidence`
- `reason`

Backend behavior:

- Validate that `confidence_delta` is negative.
- Append the contradicting or weakening evidence.
- Clamp confidence between `0.0` and `1.0`.
- If confidence drops below a minimum active threshold, mark the memory as inactive or archived.
- Regenerate `memory_embedding` if the summary or evidence changes meaningfully.

##### `archive_memory`

Marks a memory as inactive when it should no longer influence matching or planning.

Use when:

- The user explicitly corrects the system.
- The memory is clearly wrong.
- The memory has been superseded by a more accurate memory.
- The memory is stale and low confidence.

Required fields:

- `memory_id`
- `reason`
- `replacement_memory_id`, if applicable

Backend behavior:

- Set the memory status to `archived`.
- Keep the memory for audit/history rather than deleting it.
- Exclude archived memories from default retrieval and matching.
- Refresh derived profile fields.

##### `no_op`

Does not change memory state.

Use when:

- The signal is too vague.
- The signal is unrelated to social planning.
- Retrieved memories already cover the new signal well enough.
- The LLM is uncertain and should avoid creating noisy memories.

Required fields:

- `reason`

Backend behavior:

- Store the raw interaction only if needed for product analytics or conversation continuity.
- Do not change preference memories.
- Do not refresh embeddings unless another part of the interaction requires it.

Example create operation:

```json
{
  "operation": "create_memory",
  "reason": "The user expressed a new specific preference about rock climbing that is not covered by the retrieved memories.",
  "source": "notification_question",
  "memory": {
    "topic": "rock climbing",
    "summary": "Open to trying rock climbing if invited by friends, but prefers beginner-friendly low-intensity settings.",
    "evidence": [
      "answered yes to trying rock climbing if invited, with a low-intensity constraint"
    ],
    "attributes": {
      "experience_level": "beginner",
      "intensity": "low",
      "social_context": "with friends"
    },
    "confidence": 0.62,
    "source": "notification_question"
  }
}
```

Example update operation:

```json
{
  "operation": "update_memory",
  "reason": "The existing outdoor activities memory already covers beginner-friendly activities, and the new rock climbing answer refines intensity and social context.",
  "source": "notification_question",
  "memory_id": "prefmem_204",
  "changes": {
    "append_evidence": [
      "said she would try rock climbing if invited by friends, but nothing too intense"
    ],
    "set_attributes": {
      "intensity": "low",
      "social_context": "with friends"
    },
    "confidence_delta": 0.08
  }
}
```

The backend should validate proposed operations before applying them:

- Confirm referenced memory IDs exist.
- Enforce allowed fields and operation types.
- Bound confidence changes.
- Preserve existing evidence unless explicitly merged or archived.
- Reject updates based on weak or unrelated signals.
- Require user confirmation for sensitive or high-impact assumptions.

After updates are applied, the system should regenerate affected `memory_embedding` values and refresh derived profile fields such as `interest_index`, `profile_embedding`, and `summary`.

### Memory Updates

Preference memories should be updated gradually rather than overwritten aggressively.

Examples:

- If a user enjoys one board game cafe hangout, do not conclude they love all board games.
- If a user dislikes one noisy restaurant, do not conclude they dislike restaurants.
- If a user repeatedly accepts quiet coffee hangouts, strengthen the quiet/low-pressure social setting memory.

### Derived Profile Fields

The preference profile can contain derived fields for performance and retrieval:

- `summary`
- `interest_index`
- `profile_embedding`
- `preference_memory_ids`

These fields are generated from memories and should be recalculated when memories change.

### Matching Usage

Preference memories should be used in different phases:

- Candidate retrieval: use `interest_index` and `profile_embedding`.
- Compatibility scoring: compare relevant preference memories.
- Activity planning: inspect activity-specific attributes and constraints.
- Explanation: cite the memories that influenced the recommendation.
- Feedback update: strengthen, weaken, or add memories based on the result.

### Anti-Pigeonholing Rules

Convene should follow a few rules to avoid overgeneralizing:

- Never treat a broad category as the full preference.
- Prefer examples and evidence over labels.
- Track dislikes and exceptions.
- Treat old memories as weaker unless reinforced.
- Let users inspect and correct profile assumptions.
- Distinguish "likes this activity" from "likes this activity with strangers."

## 4. Matching System

The matching system selects people who are likely to have a good social experience together. It should balance compatibility, availability, novelty, user goals, and controlled randomness.

Matching should not simply pick the user with the highest similarity score. Convene should generate a pool of sufficiently compatible candidates, filter out bad fits, then choose from that pool with some randomness so the product still feels like a blind social experience.

### Matching Goals

- Find people who are compatible enough to enjoy a hangout.
- Avoid overfitting to identical interests.
- Support both new-person matching and existing-friend reconnection.
- Respect hard constraints such as time, distance, online/in-person availability, and blocked users.
- Explain why a match was selected.
- Preserve some novelty through controlled randomness.

### Matching Pipeline

1. Construct a matching request from the user's connection goal, activity filter, availability, and group-size preference.
2. Generate an initial candidate pool from the connection goal.
3. Apply safety, mode, distance, and relationship hard filters.
4. Apply availability overlap filtering.
5. Keep only candidates with at least one viable time overlap.
6. Retrieve relevant preference memories for remaining candidates.
7. Score compatibility.
8. Apply novelty/comfort preferences.
9. Select from a qualified candidate pool.
10. Generate a match explanation.
11. Pass the selected candidate or group to activity planning and final scheduling.

### Matching Request

Before matching, Convene should construct a matching request. This request separates who the user wants to spend time with from what the user wants to do.

Example:

```json
{
  "user_id": "user_001",
  "connection_goal": "meet_new_people",
  "activity_filter": {
    "include": [
      {
        "label": "coffee",
        "polarity": "include",
        "source": "user_selected",
        "activity_type": "food",
        "tags": ["coffee", "casual", "conversation_friendly"],
        "attributes": {
          "cost_level": "$",
          "supports_conversation": true
        },
        "strength": 1.0,
        "raw_text": "coffee"
      },
      {
        "label": "board games",
        "polarity": "include",
        "source": "user_selected",
        "activity_type": "games",
        "tags": ["board_games", "casual", "small_group"],
        "attributes": {
          "intensity": "low-to-medium"
        },
        "strength": 1.0,
        "raw_text": "board games"
      }
    ],
    "exclude": [
      {
        "label": "expensive restaurants",
        "polarity": "exclude",
        "source": "profile_default",
        "activity_type": "food",
        "tags": ["expensive", "restaurant"],
        "attributes": {
          "max_cost_level": "$$"
        },
        "strength": 0.86,
        "raw_text": "expensive restaurants"
      }
    ],
    "source": "mixed"
  },
  "availability_block_id": "avail_201",
  "group_size": {
    "min": 2,
    "max": 2
  }
}
```

#### Connection Goal

The connection goal describes what kind of relationship the user wants the plan to serve.

Possible values:

- `meet_new_people`
- `reconnect_with_friends`
- `either`

Behavior:

- `meet_new_people`: only consider users who are not already friends or existing connections.
- `reconnect_with_friends`: only consider existing friends or previous Convene connections.
- `either`: consider both new people and existing connections, then let scoring decide which is more appropriate.

This should stay separate from activity preferences. A user can want to meet someone new over coffee, reconnect with a friend over coffee, or allow either.

#### Activity Filter

The activity filter describes what types of activities should or should not be considered for this match.

Fields:

- `include`: activities, categories, or natural-language descriptions the user wants.
- `exclude`: activities, categories, or natural-language descriptions the user does not want.
- `source`: where the filter came from, such as `user_selected`, `availability_block`, `profile_default`, or `mixed`.

If the user explicitly selects activities for a time block, those selections should be normalized into structured activity preferences and used directly.

If the user does not select activities, Convene should infer defaults from the user's preference profile:

- `include` should be derived from high-confidence positive preference memories.
- `exclude` should be derived from high-confidence dislikes, constraints, or negative feedback.
- Low-confidence memories should not create hard excludes.

Example profile-derived filter:

```json
{
  "include": [
    {
      "label": "low-pressure games",
      "polarity": "include",
      "source": "profile_default",
      "activity_type": "games",
      "tags": ["casual", "co_op", "conversation_friendly"],
      "attributes": {
        "intensity": "low",
        "voice_chat": "optional"
      },
      "strength": 0.78,
      "raw_text": "low-pressure games"
    },
    {
      "label": "coffee",
      "polarity": "include",
      "source": "profile_default",
      "activity_type": "food",
      "tags": ["coffee", "casual", "conversation_friendly"],
      "attributes": {
        "cost_level": "$",
        "supports_conversation": true
      },
      "strength": 0.74,
      "raw_text": "coffee"
    }
  ],
  "exclude": [
    {
      "label": "high-pressure ranked games",
      "polarity": "exclude",
      "source": "profile_default",
      "activity_type": "games",
      "tags": ["ranked", "competitive", "high_pressure"],
      "attributes": {
        "intensity": "high"
      },
      "strength": 0.83,
      "raw_text": "high-pressure ranked games"
    }
  ],
  "source": "profile_default"
}
```

The activity filter should guide candidate scoring and activity planning, but it should not replace hard constraints. For example, "prefers coffee" is a soft preference, while "online only for this time block" is a hard scheduling constraint.

An activity planning agent can use the structured filter directly. The natural-language `label` and `raw_text` preserve user language, while `activity_type`, `tags`, `attributes`, and `strength` give deterministic code enough structure to retrieve activities, score candidates, and reject clear mismatches.

For MVP, this can be chosen from the user's availability block or simple social-time allocation settings.

### Candidate Generation

Candidate generation should produce a broad list before detailed scoring.

For new-person matching:

- Search seeded users or active users in the same region/timezone.
- Use `interest_index` overlap.
- Use `profile_embedding` similarity.
- Include some candidates with complementary interests.
- Exclude people already rejected, blocked, or recently matched.

For reconnection:

- Search existing connections.
- Prefer people with mutual interest to meet again.
- Consider last interaction date.
- Consider relationship strength.
- Consider overlapping availability.

### Hard Filters

Hard filters remove candidates that cannot work regardless of preference fit.

Examples:

- No overlapping availability.
- Distance exceeds user limit for in-person plans.
- Online/in-person mode mismatch.
- Blocked or hidden user.
- Age or safety policy mismatch.
- Missing required platform for online activity.
- Candidate already scheduled in that time block.

Availability filtering should happen before expensive preference-memory retrieval or LLM-based reasoning. There is no value in deeply scoring a candidate who cannot meet during the requested planning window.

### Compatibility Scoring

Compatibility should be calculated from multiple components, not one semantic score.

Possible score components:

- Preference fit
- Activity fit
- Availability fit
- Distance fit
- Social style fit
- Novelty fit
- Prior feedback fit

Example:

```text
compatibility_score =
  (0.35 * preference_fit) +
  (0.20 * activity_fit) +
  (0.15 * availability_fit) +
  (0.10 * distance_fit) +
  (0.10 * social_style_fit) +
  (0.05 * novelty_fit) +
  (0.05 * feedback_fit)
```

### Controlled Randomness

After scoring, Convene should not always choose the top candidate.

Instead:

1. Keep candidates above a minimum compatibility threshold.
2. Select from the top qualified pool.
3. Weight selection by score.
4. Adjust randomness based on the user's adventurous-to-comfortable setting.

Example:

- Comfortable: choose from top 3 candidates.
- Balanced: choose from top 5 candidates.
- Adventurous: choose from top 10 candidates, including more complementary matches.

### Match Explanation

Each match should produce a short explanation.

Example:

> Maya and Alex both like low-pressure games, are free Friday evening, and prefer small-group or one-on-one hangouts. Alex is slightly more into board games, which adds novelty without making the plan feel random.

The explanation should cite the relevant memories or signals used in matching.

## 5. Availability and Scheduling System

The availability and scheduling system determines whether a candidate can actually become a real hangout.

It has two roles:

1. Early feasibility filtering during matching.
2. Final time-slot selection after a candidate and activity have been chosen.

Availability should be checked before expensive compatibility scoring. Scheduling is mostly deterministic: either a valid time exists or it does not.

### Scheduling Goals

- Find overlapping availability between participants.
- Respect each participant's availability block constraints.
- Support online and in-person plans.
- Respect activity duration.
- Avoid double-booking users.
- Prefer times that match the user's social goals and activity context.
- Produce a clear scheduled hangout object.

### Early Availability Filtering

Early availability filtering runs during matching. Its job is to quickly remove candidates who cannot meet in the requested planning window.

Inputs:

- Matching request
- Requesting user's availability block
- Candidate users
- Candidate availability blocks
- Existing scheduled hangouts
- Planning window
- Requested mode, if known
- Minimum duration

Example:

```json
{
  "matching_request_id": "matchreq_801",
  "requesting_user_id": "user_001",
  "candidate_user_ids": ["user_014", "user_022", "user_037"],
  "availability_block_id": "avail_201",
  "planning_window": {
    "start": "2026-09-23T00:00:00-04:00",
    "end": "2026-09-30T23:59:59-04:00"
  },
  "requested_mode": "in_person",
  "minimum_duration_minutes": 60
}
```

Algorithm:

1. Expand the requesting user's availability block into concrete windows inside the planning window.
2. Subtract existing scheduled hangouts from those windows.
3. For each candidate, expand their availability blocks into concrete windows.
4. Subtract each candidate's existing scheduled hangouts.
5. Filter candidate windows by mode, such as online allowed or in-person allowed.
6. Intersect the requesting user's windows with the candidate's windows.
7. Keep overlaps that are at least `minimum_duration_minutes`.
8. Return only candidates with at least one viable overlap.

Example output:

```json
{
  "viable_candidates": [
    {
      "user_id": "user_014",
      "overlaps": [
        {
          "start_time": "2026-09-26T18:00:00-04:00",
          "end_time": "2026-09-26T21:00:00-04:00",
          "duration_minutes": 180
        }
      ]
    }
  ],
  "rejected_candidates": [
    {
      "user_id": "user_022",
      "reason": "no_overlap"
    },
    {
      "user_id": "user_037",
      "reason": "mode_mismatch"
    }
  ]
}
```

This output should be attached to the candidate set so later stages do not need to recompute overlap from scratch.

### Final Scheduling

Final scheduling runs after Convene has selected:

- Candidate or group
- Activity
- Mode
- Approximate duration
- Optional location or online platform

Final scheduling chooses the best concrete time slot and creates the hangout.

Example input:

```json
{
  "matching_request_id": "matchreq_801",
  "participant_ids": ["user_001", "user_014"],
  "activity_candidate": {
    "activity_id": "activity_401",
    "estimated_duration": {
      "value": 90,
      "unit": "minutes"
    },
    "online_or_in_person": "in_person"
  },
  "available_overlaps": [
    {
      "start_time": "2026-09-26T18:00:00-04:00",
      "end_time": "2026-09-26T21:00:00-04:00",
      "duration_minutes": 180
    }
  ]
}
```

Algorithm:

1. Revalidate participant availability to avoid stale results.
2. Filter overlaps by the selected activity's duration.
3. Filter by mode and activity constraints.
4. For in-person plans, confirm travel/location feasibility if location planning has produced a venue.
5. Generate candidate slots within each overlap.
6. Rank candidate slots.
7. Select the highest-ranked slot.
8. Create the scheduled hangout.

### Availability Blocks

Availability blocks represent times the user has made available for Convene planning.

The scheduler should treat availability blocks as hard constraints. If a user is not available in a block, Convene should not schedule them there.

Block fields relevant to scheduling:

- `start_time`
- `end_time`
- `recurrence`
- `social_goal`
- `location_constraint`
- `online_allowed`
- `in_person_allowed`

### Overlap Detection

For each participant:

1. Expand recurring availability blocks into concrete windows within the planning window.
2. Remove conflicts from existing scheduled hangouts.
3. Filter by online/in-person mode.
4. Intersect windows across participants.
5. Keep overlaps long enough for the selected activity duration.
6. Rank valid windows.

### Time Zone Handling

All stored times should include timezone offsets or be stored in UTC with a user timezone.

For display:

- Show each user times in their local timezone.
- For shared event objects, store canonical UTC timestamps.
- Preserve the originating timezone for recurring blocks.

### Ranking Time Slots

If multiple valid overlaps exist, rank them using soft preferences.

Possible ranking factors:

- Fits the requested availability block.
- Closest upcoming valid time.
- Enough buffer before/after other events.
- Preferred time of day.
- Activity-specific fit, such as dinner in the evening.
- Existing social-time allocation goals.
- Lower travel burden for in-person plans.

Example:

```text
slot_score =
  (0.30 * availability_fit) +
  (0.20 * activity_time_fit) +
  (0.15 * soonness) +
  (0.15 * buffer_quality) +
  (0.10 * social_goal_fit) +
  (0.10 * travel_feasibility)
```

### Failure Cases

If no valid time exists, the scheduler should return a structured failure reason.

Examples:

- `no_overlap`
- `duration_too_long`
- `mode_mismatch`
- `travel_not_feasible`
- `participant_unavailable`
- `candidate_already_scheduled`

Example:

```json
{
  "status": "failed",
  "reason": "no_overlap",
  "details": "Maya and Alex do not have a shared 90-minute window this week."
}
```

### Output

If scheduling succeeds, the scheduler creates a hangout candidate or final hangout.

Example:

```json
{
  "status": "scheduled",
  "hangout": {
    "participant_ids": ["user_001", "user_014"],
    "activity_id": "activity_401",
    "start_time": "2026-09-26T22:30:00Z",
    "end_time": "2026-09-27T00:00:00Z",
    "display_time": "Friday, September 26, 6:30-8:00 PM EDT",
    "mode": "in_person",
    "location": {
      "name": "Meeple & Mug",
      "address": "123 Peachtree St NE, Atlanta, GA"
    }
  }
}
```

## 6. Activity Planning System

The activity planning system chooses what the selected participant or group should do together.

Activity planning happens after early availability filtering and candidate selection, but before final scheduling. It should produce one or more activity candidates that can be scheduled.

### Activity Planning Goals

- Choose an activity that fits all participants well enough.
- Respect explicit include/exclude activity filters.
- Use participant preference memories for nuance.
- Support both online and in-person plans.
- Avoid activities that are too intense, expensive, long, inaccessible, or socially mismatched.
- Produce an activity explanation.

### Inputs

The activity planner receives:

- Matching request
- Selected participant or group
- Activity filter
- Relevant preference memories for each participant
- Available overlap windows
- Activity catalog
- Mode constraints
- Budget/distance/platform constraints

### Activity Candidate Generation

Activity candidates can come from:

- Explicit user selections
- Profile-derived activity preferences
- Shared interests
- Complementary interests
- Known activity catalog
- Event/venue search later
- Online platform availability

### Hard Activity Filters

Remove activities that cannot work.

Examples:

- Activity is in `exclude`.
- Activity duration exceeds available overlap.
- Activity requires a platform one participant does not have.
- In-person activity exceeds travel or location constraints.
- Cost exceeds budget preference.
- Activity violates accessibility constraints.
- Activity is not available during the selected time window.

### Activity Scoring

Score remaining activities using multiple components.

```text
activity_score =
  (0.30 * participant_preference_fit) +
  (0.20 * shared_interest_fit) +
  (0.15 * social_context_fit) +
  (0.10 * novelty_fit) +
  (0.10 * schedule_fit) +
  (0.10 * logistics_fit) +
  (0.05 * feedback_fit)
```

### Include / Exclude Handling

`include` preferences are positive signals, not absolute requirements unless marked as hard.

`exclude` preferences should usually be treated more strongly than includes, especially if they come from explicit user selection or high-confidence negative memories.

Example:

- Include: coffee
- Include: board games
- Exclude: expensive restaurants

Valid activity:

- Board game cafe with coffee and low cost.

Invalid activity:

- Upscale restaurant board game night with high cost.

### Online Activity Planning

Online activities should still be concrete shared experiences, not just "video call."

Examples:

- League duo queue
- Minecraft session
- Watch party
- Online board game
- Study session
- Music-sharing session
- Coding/project session

Online planning should consider:

- Required platforms
- Account ownership
- Voice/video preference
- Session length
- Skill level
- Intensity
- Whether conversation is easy during the activity

### In-Person Activity Planning

In-person activities need both an activity type and eventually a location.

Examples:

- Coffee
- Board game cafe
- Casual food
- Museum
- Walk in a park
- Study session
- Rock climbing

In-person planning should consider:

- Travel constraints
- Cost
- Venue hours
- Noise level
- Weather dependence
- Accessibility
- Whether the activity is good for a first meeting

### Output

The planner should return activity candidates, not directly create the hangout.

Example:

```json
{
  "activity_candidates": [
    {
      "activity_id": "activity_401",
      "name": "Board game cafe",
      "mode": "in_person",
      "score": 0.84,
      "estimated_duration_minutes": 90,
      "reason": "Fits both users' preference for low-pressure games, coffee, and conversation-friendly first meetings.",
      "matched_preferences": ["prefmem_101", "prefmem_219"],
      "constraints": {
        "max_cost_level": "$$",
        "requires_location_planning": true
      }
    }
  ]
}
```

### Explanation

The activity explanation should cite why it fits:

- Shared preferences
- Explicit activity filter
- Relevant memories
- Logistics fit
- Novelty or comfort level

## 7. Location Planning System

The location planning system selects a fair and feasible physical meeting place for in-person hangouts.

Activity planning chooses the kind of thing participants should do, such as coffee, bowling, or board game cafe. Location planning chooses the specific place, such as a particular cafe, bowling alley, or venue.

Location planning happens after an in-person activity candidate has been selected and before final scheduling is confirmed. It should produce one or more venue candidates that satisfy participant constraints.

### Location Planning Goals

- Find venues that match the selected activity.
- Keep travel reasonable for all participants.
- Avoid unfair travel burden.
- Respect travel radius and transportation constraints.
- Confirm the venue is open during the proposed time slot.
- Consider price, accessibility, safety, and environment.
- Produce an explanation for why the venue was selected.

### Inputs

The location planner receives:

- Participant locations
- Selected activity candidate
- Candidate overlap windows or proposed time slot
- Travel constraints
- Transportation modes
- Budget preferences
- Venue category
- Maps/Places API results or seeded venue catalog

### Maps / Places API Integration

For live in-person venue planning, Convene should use a Maps or Places API as the source of truth for venue data. An LLM with internet access can help reason about options, but it should not be the primary source for venue existence, hours, coordinates, or travel feasibility.

Maps / Places APIs can provide:

- Candidate venue search
- Venue name, address, and coordinates
- Venue category
- Hours of operation
- Price level
- Ratings/reviews
- Website or phone number
- Distance or travel time
- Open-at-time validation

The preferred split is:

```text
Maps / Places API -> venue facts, coordinates, hours, travel time
LLM / planning agent -> reasoning, ranking, explanation
```

Useful API options:

- Google Places API for venue search and metadata.
- Google Distance Matrix or Directions API for travel time.
- Mapbox, Foursquare, or Yelp Fusion as alternatives.

For a strong demo, live venue search would be valuable because it makes the generated hangout feel real. If time is limited, use a seeded demo/test venue catalog with the same normalized data shape so the rest of the planning logic can stay the same.

### Search Area Selection

Convene should not simply choose the geographic midpoint.

Instead, it should compute a fair search area based on travel time.

Possible approach:

1. Get participant coordinates.
2. Estimate travel-time reachable areas for each participant.
3. Intersect reachable areas when possible.
4. Prefer areas where travel times are reasonably balanced.
5. Search for venues within that fair area.

For a simple implementation, approximate using distance from coordinates. For a stronger demo, use travel time from a Maps API.

### Venue Candidate Search

Venue candidates can come from:

- External Places providers such as Google Places, Yelp, Foursquare, or Mapbox
- Seeded demo/test venue catalog
- Short-lived venue cache backed by provider IDs
- Event APIs later

Convene should not maintain a full production venue database. Venue data changes too often and would quickly become stale. Production venue facts should come from external Places providers.

The seeded venue catalog should be used only for:

- Local development
- Automated tests
- Demo fallback
- Hackathon scenarios where API setup is unavailable

The backend may cache normalized venue results temporarily for performance and repeat planning, but cached venue data should expire and should be refreshed from the provider before final scheduling.

Recommended provider abstraction:

```text
VenueProvider
 -> GooglePlacesProvider
 -> YelpProvider
 -> FoursquareProvider
 -> MapboxProvider
 -> SeededVenueProvider
```

Cached venue records should keep the provider identity and expiration metadata:

```json
{
  "provider": "google_places",
  "provider_place_id": "ChIJ123",
  "fetched_at": "2026-09-23T20:00:00Z",
  "expires_at": "2026-09-24T20:00:00Z",
  "normalized_venue": {
    "name": "Meeple & Mug",
    "address": "123 Peachtree St NE, Atlanta, GA",
    "lat": 33.7812,
    "lng": -84.3868,
    "hours": {
      "friday": [["12:00", "23:00"]]
    }
  }
}
```

Cache rules:

- Do not treat cached venue data as permanent truth.
- Store provider IDs so venue details can be refetched.
- Refresh hours and open status before final scheduling.
- Prefer provider data over cached data when they disagree.

Legacy or fallback candidate sources:

- Google Places API
- Yelp/Foursquare/Mapbox APIs
- Seeded venue catalog
- Event APIs

For each venue candidate, store:

- Name
- Category
- Address
- Coordinates
- Price level
- Rating
- Hours
- Tags
- Travel time from each participant
- Open during proposed slot

Example production flow:

1. Determine the activity type, such as restaurant, bowling, coffee, or board game cafe.
2. Compute a fair geographic search area from participant locations.
3. Search candidate venues using a Places API.
4. Filter venues by category, hours, price, travel radius, and availability during the scheduled window.
5. Use travel-time data to avoid unfair locations.
6. Pass valid venue candidates to the planning agent.
7. Let the planning agent rank options and generate an explanation.

### Location Planning Pipeline

Location planning should use a hybrid deterministic + agent pipeline.

```text
Selected activity candidate
 -> Venue Search Spec Builder
 -> Fair Search Area Calculator
 -> Venue Candidate Provider
 -> Venue Enrichment Service
 -> Hard Location Filter
 -> Deterministic Location Scorer
 -> LLM Venue Reranker / Explainer
 -> Selected venue + backups
```

The key implementation rule is:

```text
APIs produce facts.
Deterministic code enforces constraints.
The LLM makes soft social judgments and explanations over already-valid candidates.
```

#### Venue Search Spec Builder

Owner: deterministic backend code, optionally assisted by the activity planning agent for category mapping.

Input:

- Selected activity candidate
- Activity filter
- Participant constraints
- Proposed time slot or candidate overlap window

Output:

```json
{
  "query": "board game cafe",
  "categories": ["board_game_cafe", "cafe"],
  "required_tags": ["board_games", "conversation_friendly"],
  "excluded_tags": ["expensive", "loud"],
  "max_cost_level": "$$",
  "duration_minutes": 90,
  "time_slot": {
    "start": "2026-09-26T18:30:00-04:00",
    "end": "2026-09-26T20:00:00-04:00"
  }
}
```

Responsibilities:

- Convert an activity candidate into venue-search terms.
- Map internal activity types to external API categories.
- Preserve user constraints such as budget, accessibility, and environment.
- Decide whether location planning is required.

Example mappings:

- `board_game_cafe` -> query `board game cafe`, fallback categories `cafe`, `bar`, `game_store`.
- `bowling` -> query `bowling alley`, category `bowling_alley`.
- `coffee` -> query `coffee shop`, category `cafe`.
- `casual_food` -> query derived from cuisine tags or `restaurants`.

#### Fair Search Area Calculator

Owner: deterministic backend code.

Input:

- Participant coordinates
- Maximum travel distance or travel time
- Transportation mode
- Proposed time slot

Output:

```json
{
  "center": {
    "lat": 33.7791,
    "lng": -84.3902
  },
  "radius_meters": 5000,
  "fairness_threshold_minutes": 20,
  "transportation_mode": "driving"
}
```

Responsibilities:

- Compute the initial search center and radius.
- Avoid relying only on geographic midpoint when travel-time data is available.
- Use travel-time APIs for stronger results.
- Provide fairness parameters for later filtering/scoring.

Simple implementation:

- Use geographic midpoint.
- Search within a radius based on the smallest participant travel limit.
- Penalize unfair travel in scoring.

Stronger implementation:

- Use Distance Matrix or Directions API.
- Estimate areas each participant can reach.
- Prefer venues where participant travel times are balanced.

#### Venue Candidate Provider

Owner: integration layer.

Input:

- Venue search spec
- Fair search area

Output:

- Raw venue candidates from a seeded database or external API.

Provider options:

- `google_places_provider`
- `yelp_provider`
- `foursquare_provider`
- `mapbox_provider`
- `seeded_venue_provider`

Responsibilities:

- Fetch candidate venues from a live provider or seeded demo/test catalog.
- Normalize provider-specific responses into Convene's venue candidate shape.
- Return more candidates than needed so downstream filters have enough options.

Recommended candidate count:

- Fetch `20-40` raw venues when using live APIs.
- Keep at least `10` after basic category filtering when possible.

#### Venue Enrichment Service

Owner: deterministic backend code plus API integration layer.

Input:

- Raw venue candidates
- Participant locations
- Proposed time slot
- Transportation mode

Output:

- Enriched venue candidates.

Responsibilities:

- Attach travel time from each participant.
- Confirm whether the venue is open during the proposed slot.
- Normalize price level, rating, categories, and tags.
- Attach website, phone number, or provider URL if available.
- Mark missing data explicitly instead of guessing.

Example enriched venue:

```json
{
  "venue_id": "place_901",
  "provider": "google_places",
  "name": "Meeple & Mug",
  "category": "board_game_cafe",
  "address": "123 Peachtree St NE, Atlanta, GA",
  "lat": 33.7812,
  "lng": -84.3868,
  "price_level": "$$",
  "rating": 4.6,
  "hours": {
    "friday": [["12:00", "23:00"]]
  },
  "tags": ["board_games", "coffee", "conversation_friendly"],
  "travel_times_minutes": {
    "user_001": 14,
    "user_014": 18
  },
  "open_during_slot": true,
  "missing_fields": []
}
```

#### Hard Location Filter

Owner: deterministic backend code.

Input:

- Enriched venue candidates
- Venue search spec
- Participant constraints
- Fairness parameters

Output:

- Valid venue candidates
- Rejected venue candidates with reasons

Responsibilities:

- Remove invalid venues before LLM reranking.
- Never allow the LLM to override hard failures.
- Preserve rejection reasons for debugging and fallback behavior.

Example rejection:

```json
{
  "venue_id": "place_912",
  "reasons": ["closed_during_slot", "travel_too_far"]
}
```

#### Deterministic Location Scorer

Owner: deterministic backend code.

Input:

- Valid venue candidates
- Venue search spec
- Participant constraints

Output:

- Scored venue candidates.

Responsibilities:

- Score venues using measurable factors.
- Keep the top candidates for LLM reranking.
- Avoid sending too many venues to the LLM.

Recommended behavior:

- Score all valid venues.
- Sort by `location_score`.
- Pass top `5` venues to the LLM reranker.
- If fewer than `3` valid venues exist, pass all valid venues.

#### LLM Venue Reranker / Explainer

Owner: LLM agent called with constrained inputs.

Input:

- Top scored venue candidates
- Selected activity candidate
- Relevant participant preference memories
- Matching request activity filter
- Proposed time slot

Output:

```json
{
  "selected_venue_id": "place_901",
  "backup_venue_ids": ["place_944", "place_955"],
  "reason": "Meeple & Mug is open during the slot, balances travel well, matches the board game cafe activity, and supports a casual first meeting."
}
```

Responsibilities:

- Choose among already-valid venues.
- Prefer venues that match the social context.
- Explain the choice in user-facing language.
- Identify backup venues.

The LLM should not:

- Invent venues.
- Claim a venue is open if the API did not verify it.
- Override hard location filters.
- Use private user details in the explanation.

If the LLM output references a venue ID not in the provided candidate list, the backend should reject the output and fall back to the top deterministic venue.

### Hard Location Filters

Remove venues that cannot work.

Examples:

- Venue is closed during the proposed time.
- Venue is too far for one or more participants.
- Venue category does not match the selected activity.
- Venue exceeds budget constraints.
- Venue is missing required accessibility support.
- Venue is not appropriate for the social context.
- Travel time imbalance is too high.

### Location Scoring

Score remaining venues by fairness and fit.

```text
location_score =
  (0.30 * travel_fairness) +
  (0.20 * activity_fit) +
  (0.15 * venue_quality) +
  (0.10 * cost_fit) +
  (0.10 * environment_fit) +
  (0.10 * schedule_fit) +
  (0.05 * novelty_fit)
```

### Travel Fairness

Travel fairness should consider both total travel time and imbalance.

Good example:

- User A travels 15 minutes.
- User B travels 18 minutes.

Bad example:

- User A travels 5 minutes.
- User B travels 45 minutes.

Possible fairness metric:

```text
travel_fairness =
  1 - min(1, abs(max_travel_time - min_travel_time) / fairness_threshold)
```

### Output

The location planner should return venue candidates. Final scheduling can then confirm the exact time and create the hangout.

Example:

```json
{
  "venue_candidates": [
    {
      "venue_id": "place_901",
      "name": "Meeple & Mug",
      "category": "board_game_cafe",
      "address": "123 Peachtree St NE, Atlanta, GA",
      "lat": 33.7812,
      "lng": -84.3868,
      "price_level": "$$",
      "rating": 4.6,
      "hours": {
        "friday": [["12:00", "23:00"]]
      },
      "tags": ["board_games", "coffee", "conversation_friendly"],
      "score": 0.87,
      "travel_times_minutes": {
        "user_001": 14,
        "user_014": 18
      },
      "open_during_slot": true,
      "reason": "Fits the board game cafe activity, is open during the selected time, and keeps travel balanced for both users."
    }
  ]
}
```

### Failure Cases

If no valid venue exists, location planning should return a structured failure reason.

Examples:

- `no_venues_found`
- `no_open_venues`
- `travel_too_far`
- `travel_unfair`
- `budget_mismatch`
- `category_unavailable`

## 8. Social Graph and Reconnection System

The social graph represents relationships between users and helps Convene decide when to introduce someone new, strengthen a new connection, or reconnect existing friends.

### Goals

- Track existing friends and Convene-created connections.
- Store interaction history.
- Detect relationships that may be fading.
- Support reconnecting when both users are open to it.
- Avoid repeatedly suggesting people who do not want to meet again.
- Influence matching, scheduling, and social-time allocation.

### Relationship Types

- `existing_friend`
- `convene_connection`
- `recent_match`
- `blocked`
- `hidden`
- `rejected`

### Connection State

A connection should track:

- Users involved
- Status
- Source
- Created at
- Last interaction
- Number of hangouts
- Relationship strength
- Mutual interest to meet again
- Preferred interaction cadence
- Recent feedback

Example:

```json
{
  "id": "conn_301",
  "user_a_id": "user_001",
  "user_b_id": "user_014",
  "status": "friends",
  "source": "convene_hangout",
  "created_at": "2026-08-10T20:00:00Z",
  "last_interaction_at": "2026-08-30T23:30:00Z",
  "hangout_count": 3,
  "relationship_strength": 0.61,
  "mutual_interest_to_meet_again": true,
  "preferred_cadence_days": 21
}
```

### Relationship Strength

Relationship strength should be a derived score, not manually set.

Possible inputs:

- Number of successful hangouts
- Recency of last interaction
- Positive feedback
- Mutual desire to meet again
- Message/contact activity later
- Declines or negative feedback

Example:

```text
relationship_strength =
  (0.30 * positive_feedback_score) +
  (0.25 * interaction_frequency_score) +
  (0.20 * recency_score) +
  (0.15 * mutual_interest_score) +
  (0.10 * activity_variety_score)
```

### Reconnection Detection

A connection becomes a reconnection candidate when:

- They are already friends or previous Convene connections.
- Both users are open to meeting again.
- The last interaction is older than their expected cadence.
- There is overlapping availability.
- There is no recent negative feedback.

Example:

```json
{
  "connection_id": "conn_301",
  "reason": "Maya and Jordan usually hang out every few weeks, but they have not met in 52 days.",
  "priority": 0.78
}
```

### Reconnection Scoring

```text
reconnection_score =
  (0.30 * overdue_score) +
  (0.25 * mutual_interest_score) +
  (0.20 * availability_fit) +
  (0.15 * relationship_strength) +
  (0.10 * activity_fit)
```

### Integration With Matching

If `connection_goal` is `reconnect_with_friends`, only existing connections should be considered.

If `connection_goal` is `either`, the system should compare reconnection candidates with new-person candidates.

If a reconnection candidate scores very highly, Convene may prioritize maintaining that relationship over introducing someone new.

### Feedback Effects

Post-hangout feedback updates the social graph:

- If both users would meet again, strengthen the connection.
- If one user declines future hangouts, reduce priority or mark as one-sided.
- If feedback is negative, pause reconnection suggestions.
- If users add each other as friends, update status.

## 9. Feedback and Learning Loop

The feedback and learning loop updates Convene's understanding of users after hangouts, onboarding follow-ups, notification questions, and explicit corrections.

Feedback should improve future plans without overfitting to one interaction. A single event can update preference memories, activity preferences, relationship strength, and social graph state.

### Goals

- Capture lightweight feedback without making the user do work.
- Update preference memories gradually.
- Improve matching, activity planning, and reconnection.
- Preserve evidence for why profile changes happened.
- Avoid overgeneralizing from one hangout.
- Let users correct wrong assumptions.

### Feedback Types

Convene can learn from several signal types:

- `post_hangout_feedback`
- `notification_question`
- `onboarding_followup`
- `explicit_profile_correction`
- `decline_reason`
- `activity_acceptance`
- `activity_skip`

### Post-Hangout Feedback

Post-hangout feedback should be short and structured.

Example:

```json
{
  "id": "feedback_601",
  "hangout_id": "hangout_501",
  "user_id": "user_001",
  "rating": 4,
  "would_meet_again": true,
  "activity_fit": "good",
  "person_fit": "good",
  "comments": "The activity was fun and easy to talk during. I would prefer somewhere a little quieter next time.",
  "created_at": "2026-09-27T02:00:00Z"
}
```

### Learning Pipeline

Feedback should be processed through the same controlled memory patch system described in the Preference Profile Model section.

```text
New feedback signal
 -> classify signal type
 -> retrieve relevant preference memories
 -> retrieve relevant connection/social graph state
 -> LLM proposes memory patch and social graph updates
 -> backend validates changes
 -> apply updates
 -> refresh derived profile fields and embeddings
```

### Preference Memory Updates

Feedback can affect preference memories in several ways:

- Create a new memory.
- Append evidence to an existing memory.
- Strengthen confidence in an existing memory.
- Weaken confidence in an existing memory.
- Archive a memory if the user explicitly corrects it.

Examples:

- "The cafe was too loud" may update an environment preference toward quieter venues.
- "I liked the activity but not as a first meeting" may create context-specific activity guidance.
- "I would do this again with close friends, not strangers" should distinguish relationship context.

### Social Graph Updates

Feedback should also update relationship state.

Examples:

- If both users mark `would_meet_again = true`, increase relationship strength.
- If one user marks `would_meet_again = false`, prevent automatic reconnection unless the user later opts back in.
- If both users have multiple positive hangouts, suggest adding each other as friends.
- If feedback is negative, reduce future match priority and avoid repeated suggestions.

### Anti-Overfitting Rules

Convene should avoid making large profile changes from small signals.

Rules:

- One positive event should not create a broad permanent preference.
- One negative event should not create a broad dislike unless the user explicitly says so.
- Explicit corrections from the user should outweigh inferred behavior.
- Recent feedback should matter more than old feedback, but old evidence should remain available.
- Preference changes should store evidence and source.

### User Corrections

Users should be able to correct Convene's assumptions.

Examples:

- "I like games, just not ranked games."
- "I liked the person, but not the activity."
- "I do not want loud restaurants."
- "I am open to rock climbing, but only beginner-friendly."

Explicit corrections should usually trigger `update_memory`, `weaken_memory`, or `archive_memory` operations.

### Output

The learning loop should return a structured update result.

Example:

```json
{
  "feedback_id": "feedback_601",
  "memory_patch_applied": true,
  "updated_memory_ids": ["prefmem_101", "prefmem_244"],
  "social_graph_updates": [
    {
      "connection_id": "conn_301",
      "changes": {
        "relationship_strength_delta": 0.06,
        "mutual_interest_to_meet_again": true,
        "last_interaction_at": "2026-09-27T00:00:00Z"
      }
    }
  ],
  "derived_profile_refreshed": true
}
```

## 10. AI Agents and Deterministic Boundaries

Convene should use AI for fuzzy human interpretation and deterministic code for hard constraints.

The LLM should help interpret preferences, summarize evidence, generate explanations, and make soft social judgments. It should not be the source of truth for availability, venue facts, calendar writes, distance, or hard filtering.

### Boundary Principle

```text
LLM handles meaning.
Backend handles truth and constraints.
External APIs provide real-world facts.
```

### Agent Responsibilities

#### Profile Agent

Responsibilities:

- Converts onboarding answers into preference memories.
- Proposes memory patches.
- Summarizes user preferences.
- Generates profile-derived activity filters.

Does not:

- Directly write database records without validation.
- Delete old memories.
- Override explicit user corrections.

#### Matching Agent

Responsibilities:

- Helps explain why a match is compatible.
- May compare nuanced preference memories.
- May help identify complementary interests.

Does not:

- Select candidates who failed hard filters.
- Ignore availability constraints.
- Invent compatibility evidence.

#### Activity Planning Agent

Responsibilities:

- Chooses activity candidates from valid activity options.
- Reasons about social context and fit.
- Explains why an activity makes sense.

Does not:

- Ignore activity excludes.
- Invent platforms or capabilities.
- Choose activities that exceed available duration.

#### Location Planning Agent

Responsibilities:

- Reranks already-valid venue candidates.
- Explains why one valid venue is best.
- Considers social vibe, noise, and first-meeting suitability.

Does not:

- Invent venues.
- Claim a venue is open unless verified.
- Override Maps/Places API data.
- Override hard travel or budget filters.

#### Feedback Agent

Responsibilities:

- Interprets post-hangout feedback.
- Proposes memory patches.
- Proposes social graph updates.

Does not:

- Apply updates directly.
- Make broad conclusions from weak evidence.
- Override explicit user corrections.

### Deterministic Systems

These should be deterministic:

- Availability overlap detection
- Calendar conflict detection
- Hard filters
- Distance/travel-time calculation
- Venue open status validation
- Budget/accessibility/platform constraints
- Database writes
- Memory patch validation
- Scoring formulas
- Final scheduling
- User blocking/safety constraints

### LLM Output Contracts

All LLM calls should return structured JSON, not freeform decisions.

Examples:

- Memory patch
- Match explanation
- Activity candidates
- Venue rerank result
- Feedback interpretation

Backend code should validate:

- Required fields exist.
- IDs reference real records.
- Scores are within bounds.
- Referenced candidates were provided in the prompt.
- No hard constraints are violated.

### Failure Handling

If an LLM response is invalid:

1. Reject the response.
2. Retry once with validation errors.
3. If still invalid, fall back to deterministic behavior.
4. Log the failure for debugging.

### Explainability

User-facing explanations should be generated from actual signals:

- Preference memories
- Matching request
- Availability overlap
- Activity filters
- Venue facts
- Feedback history

Explanations should not reveal private details from other users.

## 11. End-to-End Flow and Implementation Plan

This section describes how the main Convene flow works from user input to scheduled hangout.

### End-to-End Planning Flow

1. User creates or updates profile.
2. Profile Agent converts onboarding answers into preference memories.
3. User creates a matching request.
4. Backend normalizes activity filters.
5. Matching system generates candidate pool.
6. Availability filter removes candidates without overlap.
7. Matching system scores remaining candidates.
8. Controlled randomness selects candidate or group.
9. Activity planner selects activity candidate.
10. If activity is in-person, location planner selects venue candidates.
11. Scheduler finalizes time and creates hangout.
12. After hangout, feedback loop updates memories and social graph.

### Example Flow

```text
Maya wants to meet new people Friday evening.
 -> Matching request created
 -> Activity filter defaults to coffee, casual games, low-pressure food
 -> Candidate pool generated from seeded users
 -> Availability overlap removes unavailable users
 -> Alex remains viable
 -> Preference memories show both like low-pressure games
 -> Activity planner picks board game cafe
 -> Location planner picks Meeple & Mug
 -> Scheduler confirms Friday 6:30-8:00 PM
 -> Hangout created
 -> Feedback updates preferences and connection state
```

### Implementation Phases

#### Phase 1: Data and Core Flow

- Define data models.
- Seed users, preference memories, activities, and venues.
- Implement manual availability.
- Implement matching request creation.
- Implement availability overlap filtering.
- Implement basic candidate scoring.
- Generate scheduled hangout objects.

#### Phase 2: Preference and Agent Layer

- Implement profile memory creation from onboarding.
- Implement memory retrieval by embedding.
- Implement memory patch operations.
- Add profile-derived activity filters.
- Add match and activity explanations.

#### Phase 3: Activity and Location Planning

- Implement activity catalog.
- Implement activity planner.
- Implement seeded venue provider.
- Implement location scoring and travel fairness.
- Add Maps/Places API if time allows.

#### Phase 4: Feedback and Reconnection

- Implement post-hangout feedback.
- Update preference memories from feedback.
- Update social graph.
- Add reconnection candidates.
- Add plan-my-week flow.

### Suggested Initial Build Slice

The smallest satisfying slice:

1. Seed 8-12 users.
2. Let current user fill onboarding form.
3. Generate preference memories.
4. Let user select one availability block.
5. Create matching request.
6. Filter candidates by overlap.
7. Pick from top compatible users.
8. Pick activity.
9. Pick seeded venue if needed.
10. Generate hangout.
11. Collect feedback.

### Open Questions

- Should matching optimize for one-on-one first, or include small groups early?
- How much profile editing should users have in the first version?
- Should activity filters be explicit UI controls or natural-language input first?
- Which Places provider should be used if live venue search is added?
- What privacy boundaries should exist around explanations?
